title: Standard Schema
description: Validate an environment value through a Standard Schema validator like zod, valibot, or arktype, and get the schema's output type back.
---

`parse` validates an environment value through any [Standard Schema](https://standardschema.dev) validator, zod, valibot, arktype, or your own, and returns the schema's output type. envapt carries no schema library of its own. It reads the `~standard` interface the validator already exposes, so there is no peer dependency.

```ts twoslash
import { z } from 'zod/v4';
import { Envapter } from 'envapt';
// ---cut---
const port = Envapter.parse('PORT', z.coerce.number().int().min(1024).max(65535));
//    ^?
```

A schema works on the [`@Envapt`](/docs/decorators) decorator too, through the `schema` option:

```ts twoslash
import { z } from 'zod/v4';
import { Envapt, Envapter } from 'envapt';
// ---cut---
class Config extends Envapter {
    @Envapt('LOG_LEVEL', { schema: z.enum(['debug', 'info', 'warn', 'error']) })
    static accessor logLevel: 'debug' | 'info' | 'warn' | 'error';
}
```

## Any conformant validator, or none

Because envapt reads the Standard Schema interface, a hand-written validator works with no dependency at all. The return type is inferred from the schema's output.

```ts twoslash
import { Envapter } from 'envapt';
import type { StandardSchemaV1 } from 'envapt';
// ---cut---
const positiveInt: StandardSchemaV1<string, number> = {
    '~standard': {
        version: 1,
        vendor: 'app',
        validate(value) {
            const n = Number(value);
            if (Number.isInteger(n) && n > 0) return { value: n };
            return { issues: [{ message: 'must be a positive integer' }] };
        }
    }
};

const port = Envapter.parse('PORT', positiveInt);
//    ^?
```

## Fallbacks

`parse` takes an optional third argument. On a missing value it returns the fallback.

```ts twoslash
import { Envapter } from 'envapt';
import type { StandardSchemaV1 } from 'envapt';
declare const positiveInt: StandardSchemaV1<string, number>;
// ---cut---
const port = Envapter.parse('PORT', positiveInt, 3000);
//    ^?
```

<Callout type="info">
    The fallback is returned as-is on a missing value. It does not pass through the schema. Make sure the fallback
    already satisfies the type you expect, since the schema never sees it.
</Callout>

<Callout type="warn">
    An explicit `undefined` third argument counts as no fallback. `Envapter.parse('PORT', schema, undefined)` throws
    `MissingEnvValue` on a missing value, the same as omitting the argument.
</Callout>

## Validate a group of required variables

With one `parse` call per variable, only the first bad value threw. You fixed it, deployed again, and met the next one.

[`getRequiredAll`](/docs/envapter#fail-fast-on-missing-values) checks the whole group in one call. It takes a schema for any field, next to converters, and reads every field before it throws one `SchemaValidationFailed`. The error holds the issues of every failed field in `.issues`, and each issue's `path` starts with the env key. A converter that cannot convert adds the issue `could not be converted`. A bad array element or a custom parser that throws adds its error message as the issue.

```ts twoslash
import { z } from 'zod/v4';
import { Envapter, EnvaptError, EnvaptErrorCodes, Converters } from 'envapt';
// ---cut---
function loadDatabaseConfig() {
    try {
        return Envapter.getRequiredAll({
            DATABASE_URL: Converters.Url,
            DATABASE_POOL_SIZE: z.coerce.number().int().min(1).max(100),
            DATABASE_SSL_MODE: z.enum(['disable', 'require', 'verify-full'])
        });
    } catch (error) {
        if (error instanceof EnvaptError && error.code === EnvaptErrorCodes.SchemaValidationFailed) {
            for (const issue of error.issues ?? []) console.error('invalid:', issue.path?.join('.'));
        }
        throw error;
    }
}
```

An issue message can quote the raw value, and that value may be a secret like the password inside `DATABASE_URL`. That's why the error message lists only the failed keys, and why the sample logs each issue's `path` and leaves `issue.message` out.

Missing keys are checked first and throw one `MissingEnvValue` before any schema runs. A schema default such as zod's `.default()` never applies here. Use `parse` with a fallback for an optional value.

## What throws

`parse` throws `EnvaptError` in three cases:

- The value is missing and you gave no fallback: code `MissingEnvValue`.
- The schema reports validation issues: code `SchemaValidationFailed`. The error carries every issue on its `.issues` property with the env key first in each `path`, and its message lists only the key.
- The schema's `validate` itself throws: code `SchemaThrew`, with the original error on `.cause`.

A `${VAR}` template is expanded before validation, so the schema sees the resolved value.

<Callout type="danger">
    envapt validates at config-load time and accepts synchronous schemas only. A schema whose `validate` returns a
    `Promise` is a type error, and throws `EnvaptError` with code `InvalidUserDefinedConfig` if you force it past the
    types. zod also returns a `Promise` when a `.transform` or `.refine` throws, so that throws
    `InvalidUserDefinedConfig` too. Set `Envapter.debug = 'warn'` to log the error it threw. `schema` and `converter`
    are mutually exclusive, since each one already turns the raw string into a typed value.
</Callout>
